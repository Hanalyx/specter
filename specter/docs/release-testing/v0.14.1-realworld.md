### How to read these

**Workspaces the pipeline accepts: 12 of 12.**
The harness measured only crashes and extraction
diagnostics before this column existed. Extraction is not the same
property as usability, and earlier runs reported the first while the
release notes read it as the second.

**Zero crashes is not correct extraction.** A repo the adapters
understand nothing about exits 0 and emits valid JSON, scoring
identically to one handled perfectly. The assertions-per-file column and
the ZERO marker exist so that case is visible rather than averaged away.

**The struct conflicts column cannot be non-zero here, and its zero
means nothing.** The scan iterates dependency edges with
relationship `requires`, and `reverse` emits no `depends_on`
at all: every generated workspace in this run resolves to 0
dependencies. The scan has no input, so it reports no conflicts
whether or not any exist. The column is kept because it will start
meaning something the day `reverse` emits dependency edges.

**A run over reverse output therefore cannot supply the number
`bugs/SP-SP-004` needs.** That defect is P0 and its
false-positive rate has only ever
been measured against the corpus the checker authors wrote
themselves. Measuring it on foreign code needs a corpus of specs
with real dependency edges, which reverse-compiled drafts are not.
Reading a zero here as evidence would be reading the absence of a
measurement as a passing one.

A second reason a zero can be empty: `check` refuses structural
checks while `resolve` has errors, so a row with a non-zero
resolve rc reports zeros because nothing was looked for.

**Orphan constraints are what `check` finds when it does run**, and
a non-zero count in that column is not by itself a failure.
`reverse` writes constraints that no acceptance criterion
references, which is an expected state of a draft. They are reported
at the tier default, meaning info on the tier-3 specs `reverse`
writes, so they do not fail the gate.

That was not true before `bugs/SP-SP-062` was fixed on 2026-08-23.
`reverse` stamped `enforcement: error` on every constraint it
generated, which overrode the tier default. In the v0.14.1 run both
repositories that cleared `resolve` failed `check` on it, 37 and
61 diagnostics, all `orphan_constraint`, none at info. If a row
shows resolve 0 and check non-zero, read the log: the cause is
something other than orphan constraints.
